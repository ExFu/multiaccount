## 2. Multi-account patterns observed (~15 repos)

- **Token storage**, three tiers in order of maturity:
  1. Plaintext JSON per account (`.oauth.{email}.json`, `~/.gmail-mcp/accounts/<alias>/credentials.json`) — mcp-gsuite, dmorrill.
  2. Encrypted-at-rest blob (AES-256-GCM) with key from env var or OS keychain — bakissation, marlinjai, robin-collins, Softeria.
  3. Full OS keychain/credential-manager storage with only non-secret metadata in a JSON registry — orieg, adelaidasofia. Strongest pattern; worth copying regardless of which repo is forked.
- **Account disambiguation**: dominant working pattern is an explicit `account`/`email` parameter on every tool call, resolved against an alias or raw address (aaronsb, dmorrill, orieg, bakissation, Softeria). A `manage_accounts`/`list-accounts`/`authenticate` tool lets the model discover accounts and aliases first. Softeria's ergonomic rule: default account if omitted, parameter required once >1 account exists.
- **Account aliasing**: human labels ("work", "personal", "client-x") mapped to addresses, often carrying free-text context the model can read (mcp-gsuite's `extra_info` — "this account's calendar is the one to check for meetings").
- **The stdio vs HTTP fault line matters a lot**: OAuth 2.1 multi-*user* architectures (bearer token per HTTP request) don't map onto stdio-launched local servers with one process identity. taylorwilsdon's failure to support 2 personal accounts over stdio is the clearest evidence: multi-account (one person, many accounts, local process) and multi-user (many people, shared server) are different problems with different mechanisms, and most "multi-account" marketing conflates them. The repos that solve *our* problem do it with file/keychain per-account credential stores plus an explicit account parameter — not OAuth-2.1 multi-user machinery.
- **Fan-out**: bakissation's "fan one call across all accounts" (search all inboxes at once) is the feature needed for "all my Gmails at once" and is rare — most repos make the LLM loop over accounts itself.

## 3. Google OAuth practicalities (2025/2026)

- **Testing/internal mode is fine to start.** Own Google Cloud project + OAuth client, consent screen in "Testing" status, up to 100 explicit test users (add each of your own accounts).
- **Refresh tokens expire after 7 days in Testing mode** — weekly re-auth per account unless (a) the app is published (removes the 7-day expiry and 100-user cap) or (b) re-auth is accepted as a dev-phase chore.
- **Restricted scopes** (full Gmail `https://mail.google.com/`, broad Drive) require **CASA Tier 2** assessment annually for verified/published status for *external* users. Google exempts personal use, dev/test/staging, and internal-org apps — so "just me, my own accounts" likely never needs CASA. It only bites if distributing to others as a warning-free product.
- **Phase-1 recommendation**: one OAuth client in Testing mode, own accounts as test users, narrower scopes where possible (`gmail.modify` rather than full `mail.google.com`), and a built-in per-account "reconnect" flow since 7-day refresh expiry is a given in testing mode.

## 4. ChatGPT MCP/connector support (current state)

- ChatGPT **Developer Mode** (beta since 2025-09-09; Connectors → Advanced renamed to "Plugins" in July 2026) gives full read/write MCP client support on Plus/Pro/Business/Enterprise/Education plans.
- **Transport**: streamable HTTP is the standard; SSE is being deprecated. **ChatGPT cannot reach localhost** — the server must be on public HTTPS. Tunnel (ngrok etc.) for dev; hosted endpoint for anything real.
- **Auth**: OAuth, no-auth, or mixed. OAuth supports static credentials or dynamic client registration via Client ID Metadata Documents (`none` and `private_key_jwt` token exchange).
- **Apps SDK** is the separate, heavier path (UI components + OAuth scaffolding + app-store review) for publishing to all ChatGPT users — only relevant for later distribution, not a personal connector.
- **Architectural implication**: Claude Code/Desktop happily use local stdio; ChatGPT requires public HTTPS remote. So keep the multi-account core in a provider-agnostic library, fronted by (a) a stdio MCP server for local Claude use now and (b) a remote streamable-HTTP MCP server with real OAuth for ChatGPT / claude.ai later. Don't build stdio-only if ChatGPT is a real near-term goal.

## 5. Roadmap notes (Dropbox, Microsoft, multi-provider aggregation)

- **Microsoft**: more mature and reusable than Dropbox's ecosystem. [Softeria/ms-365-mcp-server](https://github.com/Softeria/ms-365-mcp-server) is the standout — arguably a better reference implementation of the multi-account pattern than anything Google-side, because it wasn't warped by OAuth-2.1 multi-user complexity.
- **Dropbox**: no repo found with real multi-account support; the space is small, single-purpose, single-account. Build the multi-account layer ourselves, reusing token-storage patterns from the Google/Microsoft work.
- **Multi-provider aggregation ("all my inboxes")** already exists as a concept: [marlinjai/email-mcp](https://github.com/marlinjai/email-mcp) (Gmail+Outlook+iCloud+IMAP, per-account encrypted creds, cross-account transfer) and [mrchevyceleb/unified-gmail-mcp](https://github.com/mrchevyceleb/unified-gmail-mcp) (Gmail-only unified chronological inbox) — worth reading for aggregation/merge logic even if not forked wholesale.

## Recommendation

- **Best base to fork/borrow from (Google side): [aaronsb/google-workspace-mcp](https://github.com/aaronsb/google-workspace-mcp).** Actively maintained, Apache-2.0, exactly the right multi-account architecture (per-account OAuth token files under an XDG path, `manage_accounts` tooling, `email` param on every data tool, read-only-at-consent), without the multi-user OAuth 2.1 complexity that makes taylorwilsdon's bigger project the wrong shape for "one person, many accounts, stdio". Manageable TypeScript codebase, extensible to Dropbox/Microsoft later.
- **Second reference (steal patterns, not necessarily fork): [Softeria/ms-365-mcp-server](https://github.com/Softeria/ms-365-mcp-server).** Cleanest version of "single server, N accounts, one required `account` parameter, encrypted token cache backed by OS keychain" — mirror its credential-storage and account-parameter conventions, and reuse it directly when Microsoft Graph support arrives.
- **For the per-account token-file pattern and the `extra_info` idea** (telling the model what each account is for): [MarkusPfundstein/mcp-gsuite](https://github.com/MarkusPfundstein/mcp-gsuite) — quiet since April 2025, but the `accounts.json` + `.oauth.{email}.json` design is reimplementable in an afternoon and is exactly this project's original use case.
- **Build note**: given ChatGPT's public-HTTPS + real-OAuth requirement versus Claude Code's stdio preference, plan the account-management/token-store core as a standalone library from day one, with two thin MCP transport wrappers (stdio now, streamable-HTTP later) rather than baking multi-account logic into one server's request handling.
